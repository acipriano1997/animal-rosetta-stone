# Workbench presentation localization

English (`static/locales/en.json`) is the source and default presentation catalog.
`presentation.py` renders an English shell and safely embeds that catalog, so
fallback does not need a catalog fetch. `i18n.js` changes only explicitly marked
chrome text/attributes. `app.js` renders scientific values as escaped,
direction-isolated `data-canonical` elements outside translation subtrees.
Presentation code is not imported by stores, canonical adapters, producers,
evidence grading, claims or comparison gates.

## Ownership and protected values

Catalogs own navigation, field labels, loading/error/empty messages and interface
instructions. Scientific authorities retain ownership of **all API values**:
IDs; RQ/H/D/RUN/CRG codes; enums and dispositions; provenance IDs, hashes,
DOIs and source identifiers; taxonomic names; source quotations; scientific
claims and hypotheses; interpretation ceilings; rights, missingness and
comparison states. These are never looked up in a catalog or translated.
Unknown source-field names are displayed verbatim rather than guessed.

Numeric row counts may be formatted for presentation; scientific metrics retain
their original JavaScript numeric representation and precision. Empty display
placeholders describe an absent value only; they do not create a missingness
code, outcome or disposition. Canonical source prose, including registry-absence
rules and rights/media consequences, remains verbatim. All language choices use
identical API URLs and payloads. Headers, cookies and locale query parameters
never select, alter or persist scientific state. Only the preference key
`ars.workbench.presentationLocale` is written to browser local storage.

Real scientific translations require explicit future governance, provenance,
review and source-language metadata. Adding a presentation catalog does not
authorize translating any scientific material or promoting a gate.

## Locale selection and failure behavior

Only allowlisted `en` and `en-XA` are supported. Matching is case-insensitive;
all other values, including regional variants, deterministically resolve to
English. Browser language and `Accept-Language` do not change the default.
The native labeled selector persists the chosen locale when storage is available;
denied storage leaves it usable for the current page. Document `lang` and `dir`
follow the resolved locale. Fetch, parse or timeout failures restore English,
reset the selector and announce the fallback. The last selection wins during
concurrent catalog loads. Missing or invalid messages fall back per key to
English, with an explicit `MISSING` marker in the test locale.

Language changes update existing chrome nodes without replacing controls,
moving focus, re-requesting scientific data or closing disclosure elements.
Canonical elements keep their own English language annotation for the current
authorities, `dir="auto"` and `translate="no"`; translations must not overwrite
that boundary.

## Pseudo-localization and verification

`en-XA` is **testing only**, not an approved scientific or human translation.
The generator adds accents, Unicode expansion and visible brackets while
preserving interpolation placeholders. Language names stay readable so users
can return to English. Never hand-edit `en-XA.json`.

```bash
python scripts/generate_workbench_pseudolocale.py
python scripts/generate_workbench_pseudolocale.py --check
python -m pytest -q tests/test_workbench_presentation.py
```

Use Node.js 22+ on `PATH`; there are no npm or translation-service dependencies.
Ordinary pytest runs include catalog completeness, deterministic generation,
packaged resource configuration, escaped shell output, source ownership,
socket-free HTTP/API invariance and actual JavaScript module execution with
small DOM doubles. The doubles verify locale lifecycle, fallback, race handling,
focus, protected nodes and application rendering; they do not emulate layout or
screen readers. CI installs Node, checks generated bytes without modifying files,
then runs the ordinary suite including the existing socket tests and checks the
assets in a built wheel using the pinned packaging dependencies.

## Adding a future approved presentation locale

1. Obtain presentation review/approval for the scope. Keep every protected field
   above outside the catalog. Copy English keys to a UTF-8 `<locale>.json` file;
   preserve named placeholders and use plain text, never markup.
2. Register the locale in `i18n.js` with its explicit `direction`, formatting
   locale and `testOnly: false`. Add its exact file path to the server's static
   allowlist and its native language name to the selector with the appropriate
   `lang`. Preserve English fallback and a readable way to return to English.
3. Extend completeness, fallback, packaging, document-language and API-invariance
   tests for the new locale. Regenerate the pseudo-locale if English changes.
4. Review rendered output, keyboard navigation, screen-reader names and narrow
   layouts before release. Review any RTL locale with a fluent reviewer; en-XA
   exercises expansion and Unicode, not RTL linguistic correctness.

## Accessibility and layout audit

The selector uses a native label and description, with polite status feedback.
Navigation focuses its destination; the skip link targets focusable main content.
Focus is visible, reduced-motion preference is honored, corpus buttons expose
their selected state and result target, and provenance links announce new tabs.
Tables have column header scope. Busy/error states are announced without making
the entire scientific record a live region.

Flexible controls, wrapping text, shrinkable grids and logical alignment/margins
accommodate expansion and future RTL chrome. Canonical values are bidi-isolated
and preserve whitespace. Host/browser release checks should cover keyboard-only
navigation, changing locale with a disclosure open, blocked storage, slow catalog
loads, 320px width, 200–400% zoom, long identifiers and a temporary RTL document
direction. Native select menus may use platform scrolling for long labels.
